## P0 — 게임 구조와 편집 가능성을 막는 것

### P0-1. C++ 호출 비용 줄이기 (묶어 보내기·변경분만 보내기)

**문제**
- 사용자 C++는 별도 worker 프로세스에서 돌고, 호출마다 장면 정보를 JSON으로 주고받습니다(`tools/native-host.mjs`, `prototype/native-transport.js`).
- 그래서 C++를 부르는 BP 인스턴스 수에 비례해 프레임 시간이 늘어납니다.

**실측 (Auric Loop, 화면 없는 실행, 600프레임, Dungeon_3 장면 약 130개 오브젝트)**
- 기본 장면: 35ms/프레임 (첫 실행은 109ms).
- 같은 C++ BP 인스턴스 9개가 Tick마다 빈 함수 `EnemyStats::Think(delta)`를 부를 때: **270~360ms/프레임**. 호출 1회에 약 25~35ms입니다.
- 엔진 인계 문서 기준으로도 RPC가 14.7ms, worker 평균이 9.31ms입니다(parse 1.04 / patch 7.61 / sync 0.40).

**영향**
- 언리얼·유니티처럼 적·문·NPC·투사체마다 BP를 두고 각자 Tick에서 C++를 부르는 구조를 쓸 수 없습니다.
- 지금은 C++ 클래스 하나가 모든 적·탄·문을 한 번에 계산하는 우회 구조입니다. 그래서 기획자가 적 종류별로 고칠 수 있는 단위가 없습니다.

**필요한 것 (순서대로)**
1. **프레임 단위 묶음 전송**
   - 한 프레임 동안 같은 빌드에 가는 모든 C++ 호출(모든 인스턴스의 Tick·이벤트·함수)을 RPC 1회로 묶습니다.
   - 결과도 한 번에 적용합니다.
   - 호출 순서와 BP 실행 순서는 지금과 같게 유지합니다. 같은 프레임 안에서 앞 호출의 결과를 뒤 호출이 보아야 하면, 그 경계만 따로 처리합니다.
2. **변경분만 동기화**
   - 매 호출마다 전체 장면을 보내지 않습니다. 첫 동기화 뒤에는 바뀐 Transform·속성·풀 상태만 보냅니다.
   - 지금 `patch 7.61ms`가 대부분이라 여기서 가장 많이 줄 것으로 봅니다.
3. **(장기) 같은 프로세스 실행**
   - 사용자 C++를 DLL로 엔진 프로세스 안에서 돌리는 방식입니다. BUILD_PLAYER_RESEARCH의 "DLL 교체" 항목입니다.
   - 1·2번으로 목표에 닿으면 미뤄도 됩니다.

**완료 기준**
- [x] Auric Loop 방 장면(약 130개 오브젝트)에서 C++ Tick을 부르는 BP 인스턴스 50개, 60fps 기준: 사용자 C++ 호출 추가 비용 **프레임당 2ms 이하**(편집기 실행과 배포 Game.exe 각각).
- [x] 같은 조건에서 화면 없는 실행기가 600프레임을 기본 장면 대비 1.5배 이하 시간에 끝냄.
- [x] 기존 `TopDownShooter` 데모 검사 9개 통과, 결과 수치 동일.
- [x] Android 기기(또는 에뮬레이터)에서 같은 50개 인스턴스 장면이 30fps 이상.

### P0-2. 같은 C++ 빌드 안 인스턴스끼리 실제 객체 접근

**문제**
- 같은 헤더·구현 파일에 클래스 두 개를 둔 실험입니다.
  - `TopDownShooter`(중앙 규칙)와 `EnemyStats`(적 값, `HB_PROPERTY float MaxHp`)를 만들었습니다.
  - `BP_ZEnemy`(부모 C++ `EnemyStats`, 기본값 `MaxHp = 7.25`)를 적 오브젝트에 붙였습니다.
- 결과:
  - 그 오브젝트의 `nativeClass = EnemyStats`, `nativeProperties.MaxHp = 7.25`는 정상이었습니다.
  - 하지만 `TopDownShooter::Update`가 배열로 받은 그 오브젝트의 포인터는 `typeid = hb::Actor`였고, `dynamic_cast<EnemyStats*>`는 `nullptr`였습니다.
  - 그 오브젝트가 직접 Tick에서 C++를 부르게 해도 같았습니다.
- 즉 중앙 C++가 다른 인스턴스의 C++ 값과 함수에 접근할 수 없습니다.

**영향**
- "적 BP마다 체력·속도·공격력·그림을 정하고, 계산은 중앙 C++ 한 곳에서" 하는 구조가 불가능합니다. P0-1을 피할 유일한 대안인데 막혀 있습니다.
- 언리얼의 `Cast<AEnemy>(Actor)->MaxHp`, 유니티의 `GetComponent<Enemy>().maxHp`에 해당하는 기능입니다.

**필요한 것**
1. 같은 빌드의 인스턴스는 한 worker 안에 **실제 클래스 객체**로 존재해야 합니다. 함수 인자·배열·찾기 결과로 받은 `hb::Actor*`가 그 실제 객체를 가리켜서 `dynamic_cast`가 동작해야 합니다.
2. 다른 빌드(다른 C++ 파일)의 인스턴스에는 이름으로 속성을 읽고 쓰고 함수를 부르는 통로를 둡니다.
   - 읽기·쓰기: `hb::Native::GetFloat(actor, "MaxHp")`, `SetFloat`.
   - 함수 호출: `hb::Native::Call(actor, "TakeDamage", args)`.
3. 속성 쓰기를 한 경우, 그 값이 BP 쪽 `nativeProperties`와 편집기 디버그 표시에도 반영돼야 합니다.

**완료 기준**
- [x] 위 실험 그대로: 중앙 C++가 `dynamic_cast<EnemyStats*>(enemies[0])->MaxHp == 7.25`를 읽고, 값을 바꾸면 다음 프레임 `nativeProperties`에 보입니다.
- [x] 장면 전환·Stop/Play 반복 뒤에도 포인터가 유효하고, 풀 반환·재사용 시 같은 객체를 가리킵니다.
- [x] 다른 빌드 객체에 `hb::Native::GetFloat`·`Call`이 동작합니다.

### P0-3. BP→BP 상속과 배치한 오브젝트별 값 덮어쓰기

**문제**
- `docs/BLUEPRINT_SPEC.md` 클래스/상속 행의 "남은 범위"에 BP→BP 상속, 부모 호출, 인스턴스별 override가 있습니다.
- 확인 결과:
  - 장면 오브젝트에 직접 넣은 `nativeProperties`는 무시됩니다. `play-world.js`가 BP 기본값으로 덮어씁니다.
  - 그래서 값을 다르게 하려면 BP 파일을 통째로 복사해야 했습니다. `BP_Hub`, `BP_Test_Sherry`, `BP_Test_Alea`는 `BP_TopDownShooter`의 사본이고, 각자 C++ 원문 사본까지 들고 있습니다.

**필요한 것**
1. **BP 부모를 다른 BP로 지정** (`settings.parentClass`에 BP 경로).
   - 자식은 부모의 컴포넌트·변수·그래프·C++ 부모를 물려받습니다.
   - 기본값과 이벤트를 덮어쓸 수 있고, "부모 호출" 노드가 있어야 합니다.
2. **배치한 오브젝트별 값 덮어쓰기**: 장면 오브젝트에 `overrides: {변수/속성: 값}`을 저장합니다.
   - 세부 패널에서 바꾼 값은 굵게 표시하고, "기본값으로 되돌리기"를 둡니다.
   - 실행·배포·C++ 기본값에 모두 반영합니다.
3. 부모 BP를 고치면 자식 BP와 배치한 오브젝트에 자동 반영합니다. 덮어쓴 값은 유지합니다.
4. 순환 상속 금지와 이름 바꾸기 redirect가 필요합니다.

**Auric Loop에서 쓸 구조**
```text
EnemyStats (C++ 부모: MaxHp, Speed, ContactDamage, Ranged, ShotInterval, ShotCount, Sprite …)
  └ BP_Enemy (공통: 피격 깜빡임, 쓰러짐 연출, 드롭 골드)
      ├ BP_Skeleton        (근거리)
      ├ BP_SkeletonMage    (원거리 3갈래)
      └ BP_SkeletonCaptain (보스, 패턴 표)
BP_Interactable (C++ 부모: Prompt, Text, Price …)
  ├ BP_NPC_Collector / BP_NPC_Interior / BP_ClosedShop(문구만 덮어씀)
  └ BP_Furniture_Sofa / Bed / Fridge / TV
BP_Door, BP_GatherNode(광물·약초), BP_SpawnPoint(방마다 적 등장 자리)
```

**완료 기준**
- [x] 위 계층을 편집기에서 만들고, 장면에 `BP_Skeleton` 3개를 놓은 뒤 하나만 `MaxHp = 10`으로 덮어씁니다. 실행 시 그 하나만 10, 나머지는 부모 값입니다. 배포 Game.exe에서도 같아야 합니다.

### P0-4. 실행 중 생성·찾기 (Spawn, 클래스/태그로 찾기)

### P1-6. 소리: C++ API, 그리고 소리 때문에 멈추지 않기

**문제**
1. C++에는 소리 재생 API가 없습니다(`AudioMixer`만 있음).
   - 그래서 C++가 `BlueprintImplementableEvent`인 `OnPlaySfx(Sound)`, `OnPlayMusic(Music, Previous)`를 부르고, BP가 Play Sound / Stop Sound로 재생합니다.
2. **사용자 입력 전에 Play Sound를 부르면 VM 전체가 멈춥니다.**
   - 원인은 `engine-services.js`의 sound 처리입니다. `soundRouting.connect`와 `player.play()`를 await하는데, AudioContext가 suspended 상태라 끝나지 않는 것으로 봅니다.
   - 편집기 자동 조작(runtime.play)으로 실행하면 `time = 0.0195`에서 멈춘 것을 확인했습니다.
   - 데모는 배경음을 "타이틀에서 첫 키를 누른 뒤"로 미뤄서 피했습니다.
3. 화면 없는 실행기(`tools/run-project.mjs`)는 `sound`, `playSoundAt`, `stopSound`를 만나면 예외를 던집니다(`화면/음향 실행 검사가 필요한 기능`).
   - 그래서 데모 C++에 `AURIC_MUTE` 환경 변수 우회를 넣었습니다.

**필요한 것**
1. C++ API:
   - `hb::Audio::Play(asset, volume = 1, pitch = 1) -> handle`, `Stop(handle)`.
   - `PlayMusic(asset, fadeSeconds)`, `StopMusic(fadeSeconds)`.
   - 위치 음향 `PlayAt(asset, position)`, 믹서 버스 지정.
2. AudioContext가 아직 시작되지 않았으면 재생 요청을 큐에 넣고 **즉시 반환**합니다. 첫 사용자 동작 때 배경음은 이어 재생하고, 효과음은 버립니다. VM은 절대 기다리지 않습니다.
3. 화면 없는 실행기에서는 소리 연산을 실패시키지 않고 `visualEvents`(또는 `audioEvents`)에 기록만 합니다. 검사에서 "어떤 소리가 몇 번 났는지" 확인할 수 있어야 합니다.
4. 편집기 자동 조작으로 실행할 때 "사용자 동작 있음"으로 표시하는 옵션이 필요합니다(`runtime.play {userGesture: true}`).

**완료 기준**
- [ ] Auric Loop에서 BP 소리 이벤트 그래프를 지우고 C++ `hb::Audio`만으로 효과음 16종·배경음 4곡이 재생됩니다(편집기, Game.exe, Android).
- [ ] 첫 프레임에 배경음을 요청해도 게임이 멈추지 않고, 첫 입력 뒤 들립니다.
- [ ] `AURIC_MUTE` 없이 `tools/check_demo.mjs` 9개가 통과하고, 각 검사에서 소리 기록 개수를 확인할 수 있습니다.

## P2 — 편집기 작업 흐름·렌더·검사·배포

### P2-11. 편집기

**실제로 겪은 문제**
1. **장면을 열면 빈 화면**
   - 뷰포트 카메라가 문서별이 아니라 전역(`hbengine.viewport.camera`) 하나입니다.
   - 그래서 거점(y −34)이나 보스방(y 96)에 있는 장면을 열면 (0, 0)만 보입니다.
   - 데모는 장면마다 내용을 (0, 0)으로 옮겨서 피했습니다.
2. **"외부에서 변경된 에셋이에요" 때문에 저장·종료가 막힘**
   - `native.build`를 하면 BP 문서가 dirty가 됩니다.
   - 밖에서(AI·스크립트·git) 파일을 바꾸면, 그 편집기에서는 저장도 다시 읽기도 막힙니다.
3. **C++ 원문 사본**
   - BP마다 C++ 헤더·구현 원문 사본과 클래스 정보를 들고 있습니다.
   - 그래서 같은 C++를 쓰는 BP 4개(`BP_TopDownShooter`, `BP_Hub`, `BP_Test_*`)를 매번 같이 동기화해야 합니다(`tools/sync_cpp.mjs`).
   - 하나라도 빠지면 `외부 C++ 변경 후 빌드가 필요해요` 오류가 납니다.
4. **원문 비교가 바이트 단위**: CRLF/LF가 다르면 빌드가 필요하다고 나옵니다(`.gitattributes -text`로 우회).
5. **편집기가 문서 사본을 먼저 복원**: `Saved/Editor/storage.json`에 열린 문서 사본을 두고 디스크보다 먼저 복원해서, 밖에서 바꾼 장면이 안 보였습니다(직접 지워서 우회).
6. **자동 조작의 키 입력이 사라짐**: 창이 포커스가 없거나 최소화돼 있으면 `runtime.input` 누름이 사라지거나 캡처가 안 됩니다.

**필요한 것**
- 문서(장면)별 뷰포트 카메라를 저장합니다. 처음 열면 "전체 맞춤".
- 디스크 변경 감시:
  - dirty가 아니면 자동으로 다시 읽습니다.
  - dirty면 "디스크 것 받기 / 내 것 저장 / 비교" 선택창을 띄웁니다.
  - `storage.json` 복원보다 디스크 최신을 우선합니다.
- `native.build`는 문서를 dirty로 만들지 않습니다(빌드 결과는 별도 캐시에 둡니다).
- BP는 C++ 경로와 해시만 저장합니다. 원문은 `Source/`가 유일한 원본이고, 같은 파일을 쓰는 BP는 자동으로 같이 갱신됩니다.
- 원문 비교는 줄바꿈과 BOM을 무시합니다.
- 자동 조작 입력은 창 포커스·최소화와 상관없이 실행 월드에 들어가야 합니다(자동 조작 세션 표시). 최소화 상태에서도 캡처할 수 있으면 좋습니다(오프스크린 렌더 캡처).

**완료 기준**

## P0 적용 후 Auric Loop 이전에서 새로 확인한 엔진 쪽 문제 (Claude, 2026-10-06)
